# RentMont

Монитор Sreality.cz: аренда **квартиры целиком** в **Brno-město**, базовая аренда **строго < 13 500 Kč/мес.**, проверка каждые **10 минут**. Коммунальные не входят в порог. Факты извлекаются через **gpt-5.4-mini**, уведомления приходят в Telegram по умолчанию с максимум **3 фото** (`TELEGRAM_MAX_PHOTOS`, 0–10).

Сервис написан на Go и лежит в `service/`.

## Запуск

Нужен Go 1.24+. Скопируй `.env.example` в `.env`, заполни `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Подписка ChatGPT не заменяет оплату OpenAI API. Отправь боту `/start`, прежде чем использовать личный чат.

Настройки читаются из `.env` в текущем каталоге и из переменных окружения (переменные окружения важнее), поэтому запускай из корня репозитория:

```bash
go -C service build -o ../rentmont ./cmd/rentmont
./rentmont --once
./rentmont
# Принудительно повторить извлечение текущих объявлений:
./rentmont --once --reextract
```

Дополнительно поддерживается `OPENAI_BASE_URL` (по умолчанию `https://api.openai.com/v1`). `Ctrl+C`/`SIGTERM` останавливают процесс.

Процесс должен оставаться запущенным. Для 24/7 используй VPS/systemd, Windows Task Scheduler или Docker. **Только один процесс на DATA_DIR**: межпроцессных блокировок нет.

По умолчанию первая успешная проверка сохраняет подходящие объявления как `suppressed`, без Telegram-спама. Для уведомлений сразу установи `NOTIFY_EXISTING=true` до первого запуска. Первичная обработка всё равно расходует OpenAI API.

## Docker

Нужны Docker Engine / Docker Desktop (Linux containers) и Docker Compose v2.
Настройки берутся из `.env`; ключи и локальные данные не копируются в образ.
`./data` подключается в контейнер как `/app/data`, поэтому состояние сохраняется при пересоздании контейнера. `DATA_DIR` внутри Compose фиксирован на `/app/data`.

```bash
docker compose up -d --build
docker compose logs -f --tail=100
docker compose down
```

Образ многоступенчатый: сборка в `golang:1.27-alpine`, запуск статического бинарника в `gcr.io/distroless/static-debian12` (от root внутри контейнера). В rootless Docker это не root хоста; подключённый каталог `./data` должен быть доступен пользователю, запустившему Docker. В обычном rootful Docker созданные файлы могут принадлежать root хоста.
Не запускай локальный монитор одновременно с контейнером: процесс на каталог данных должен быть один.

Разовая проверка (сначала останови постоянный контейнер):

```bash
docker compose stop rentmont
docker compose run --rm --build rentmont --once
# Принудительное обновление источника и извлечения:
docker compose run --rm rentmont --once --reextract
docker compose up -d
```

После изменения кода пересобери образ: `docker compose up -d --build`.
После изменения `.env` пересоздай контейнер: `docker compose up -d --force-recreate`.
Политика `unless-stopped` перезапускает контейнер после завершения процесса, включая ошибки; причину смотри в логах. Ротация логов ограничена тремя файлами по 10 МБ.

## Разделение ответственности

```text
service/
  cmd/rentmont/         # CLI, цикл опроса, сигналы
  internal/config/      # настройки из .env/окружения
  internal/domain/      # контракты фактов, файлов и общего состояния; строгая валидация JSON
  internal/filters/     # чистая политика отбора, без сохранения решений
  internal/sreality/    # внешнее API, адаптер raw → SourceListing, расстояние до центра
  internal/extraction/  # хеши, whitelist входных полей, OpenAI → RentalDetails
  internal/telegram/    # форматирование, скачивание фото, отправка без доступа к БД
  internal/storage/     # отдельные атомарные файлы на объявление
  internal/monitor/     # обновление, отбор, orchestration доставки
  internal/pyjson/      # json.dumps/str() в стиле Python для совместимых хешей
  internal/jsonval/     # доступ к нетипизированным JSON-значениям
  internal/netutil/     # HTTP с лимитами; ошибки без URL (в URL Telegram есть токен)
```

`SourceListing` — проекция сырого объявления для фильтрации и отображения. `RentalDetails` — только извлечённые факты: `payments`, `is_room_rent`, `area_m2`, `available_from`, `furnishing`. `Listing` — публичная проекция `{source, rental}` для Telegram и экспорта. Внешние зависимости сервиса (`Source`, `Extractor`, `Notifier`) заданы интерфейсами в `internal/monitor`.

## Хранение: отдельная папка на объявление

```text
data/
  state.json
  listings.json
  <id>/
    source.json
    extraction.json
    notification.json
```

Формат совместим с Python-версией: каталог `data/`, созданный ею, читается без миграции.

`state.json` содержит только общее состояние монитора, формат **v4**:

```json
{
  "schema_version": 4,
  "initialized": false,
  "current_search_ids": []
}
```

В папке каждого объявления файлы независимы:

- `source.json`: `{raw, first_seen_at, last_seen_at}`. Полный detail из API, независимо от результата фильтрации. `last_seen_at` — время последнего скачивания detail. Данные обновляются каждый цикл; `first_seen_at` сохраняется.
- `extraction.json`: `{global_hash, llm_hash, details, extracted_at}`. Успешный результат LLM, включая комнаты, неизвестную аренду и превышение бюджета. Файл отсутствует до первого успешного извлечения.
- `notification.json`: `{status, sent_at, chat_id, message_ids, telegram_method, telegram_response, format_version, gone_at, gone_notified}`. Для `sent` сохраняются время отправки, фактический ID чата, все ID сообщений, метод API и полный JSON-ответ Telegram. Для альбома `message_ids[0]` соответствует сообщению с подписью. Для `suppressed` метаданные отправки пустые. Отсутствие файла означает «ещё не уведомляли».

`current_search_ids` обновляется только после успешного завершения поиска. Исчезнувшие объявления остаются в архиве, но не участвуют в текущем экспорте и доставке. Ошибка поиска сохраняет предыдущий набор ID, однако доставка в этом цикле не выполняется.

Каждый файл читается по необходимости и сохраняется атомарно: временный файл записывается и заменяет основной. Обновление источника не перезаписывает извлечение или уведомление. Записи строго валидируются (неизвестные поля, обязательные ключи, типы, диапазоны); ID — только цифры и должен совпадать с ID внутри source. При ошибке чтения/сохранения монитор останавливается. Повреждённые файлы не сбрасываются автоматически.

Общей транзакции между файлами нет: после сбоя может остаться source без extraction — следующий цикл закончит обработку. Состояние доставки сохраняется только после успешной отправки.

Сырой ответ API может содержать контактные данные: база локальная, `data/` исключён из Git. В OpenAI передаётся только whitelist полей описания и платежей, не контакты и фотографии.

## Лимиты бюджета

`MAX_RENT_KC` — строгий лимит базовой аренды (по умолчанию 13500).
Дополнительно можно задать в `.env` `MAX_RENT_AND_UTILITIES_KC=17000`: если известны **обе** суммы, объявление проходит только при `rent_kc + utilities_kc < MAX_RENT_AND_UTILITIES_KC`. При неизвестных коммунальных дополнительная проверка пропускается; неизвестная аренда по-прежнему отсекается основным фильтром. Комиссия и залог в сумму не входят.

Если `MAX_RENT_AND_UTILITIES_KC` не задан, дополнительный лимит отключён. Значение должно быть положительным целым числом. Проверка выполняется по извлечённым фактам, не ограничивает поиск API и не требует повторного вызова LLM при изменении лимита.

## Обновления и фильтрация

1. Получить полный текущий поиск и сохранить его ID.
2. Получить свежий detail каждого текущего объявления и сохранить сырой ответ.
3. Построить `SourceListing` и проверить категорию, район, API-цену.
4. Вычислить `global_hash`: SHA-256 названия, описания, цены (`price_czk`, единицы и валюты), примечания к цене, ежемесячных расходов (`cost_of_living`), комиссии (`commission`), залога, меблирования (`furnished`) и дат `since`/`edited`. Отдельно вычислить `llm_hash` по версии контракта экстракции (`extraction.Version`) и всем полям `extraction.Fields`, фактически передаваемым в LLM: включая площадь, дату заселения и признак отсутствия комиссии, но без дат публикации/редактирования. Использовать извлечение с совпадающим `llm_hash`; иначе вызвать LLM.
5. Немедленно сохранить успешное извлечение до применения бизнес-фильтра.
6. Применить текущие правила к фактам; собрать подходящие объявления этого цикла.
7. Обновить экспорт, отредактировать изменившиеся отправленные объявления и отправить новые без `sent`/`suppressed`.

Хеши сериализуются так же, как `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))` в Python (`internal/pyjson`), поэтому значения, сохранённые Python-версией, остаются валидными.

Оба хеша хранятся в `extraction.json`, а их отправленные версии — в `notification.json`. Несовпадение любого хеша вызывает редактирование исходного сообщения или подписи первого фото без повторной отправки и замены фотографий. Если изменились только даты, факты LLM используются повторно, `global_hash` обновляется без изменения `extracted_at`. Фото и их лимит не входят в хеши и не вызывают редактирование. Старое поле `content_hash` при чтении отбрасывается. Ошибка Telegram оставляет обновление для повторной попытки. Старые извлечения без `llm_hash` или с предыдущей версией контракта пересчитываются один раз. Изменение модели или промпта без повышения версии требует `--reextract`: флаг принудительно перепарсивает текущие объявления, прошедшие исходный фильтр. При ошибке LLM старые факты сохраняются, но не используются для обновления изменившегося объявления; следующий цикл повторит извлечение.

Запросы к OpenAI используют Structured Outputs (строгая JSON-схема `RentalDetails`) и повторяются до двух раз при сетевых ошибках, 408/409/429 и 5xx. Ответ дополнительно валидируется: отрицательные суммы, невалидные даты и неизвестные значения отклоняются, нулевые суммы превращаются в `null`. Фильтры применяются каждый цикл независимо от сохранённых фактов. Неудачная доставка не создаёт запись `sent`, поэтому повторяется после следующей успешной проверки.

Поиск ограничен API-ценой до LLM: объявления с общей API-ценой выше порога, но базовой арендой ниже него могут быть пропущены.

## Экспорт и факты

`data/listings.json` — массив подходящих объявлений последней завершённой проверки, каждое в формате `{source, rental}`. Внутренние состояния не экспортируются.

- `source`: ID, название, ссылка, категории, район, API-цена, до `TELEGRAM_MAX_PHOTOS` фото, расстояние, даты публикации/редактирования.
- `source.furnishing`: `furnished`, `partially_furnished`, `unfurnished` или `null`. Берётся из структурированного поля API `furnished.value` (1, 3, 2 соответственно); 0, отсутствие или неизвестный код — `null`. Имеет приоритет при отображении в Telegram и учитывается в `global_hash`, но не передаётся в LLM.
- `rental.furnishing`: те же значения, извлечённые LLM из явных указаний в названии/описании. Используется в Telegram только при `source.furnishing=null`.
- `rental.payments`: `rent_kc`, `utilities_kc`, `commission_kc`, `deposit_kc`. Все суммы в Kč. Аренда и коммунальные ежемесячные; комиссия и залог разовые. Неизвестные, неоднозначные и нулевые суммы — `null`.
- `is_room_rent=true` при явной аренде комнаты/места; категория `Pokoj` отсекается до LLM.
- `area_m2` — площадь из объявления, неизвестная — `null`.
- `available_from`: `null`, `"asap"` или дата `YYYY-MM-DD`, без угадывания неполных дат.
- `published_at`/`updated_at` берутся из `since`/`edited`; отсутствующие/невалидные — `null`.
- `distance_to_center_km` — по прямой до náměstí Svobody (49.1951, 16.6080), округление до 0,1 км; без координат — `null`.

## Telegram

Версия шаблона задаётся константой `FormatVersion` в `service/internal/telegram/format.go`.
При изменении форматирования повышай её. Успешно отправленная/обновлённая версия сохраняется
в `notification.json` как `format_version`. Несовпадение версии (включая отсутствие поля)
вызывает редактирование текста/подписи существующего сообщения, даже если оба хеша совпадают.
LLM для этого не вызывается, новые сообщения и фото не отправляются. Ответ Telegram
«message is not modified» тоже считается успехом.

Название — кликабельная ссылка. Сообщение содержит аренду и коммунальные с итогом, комиссию и залог без суммирования, заселение, меблировку, локацию и даты. Локация: `📍 Loc: Černá Pole ≈1.2 km to center`, где название района — ссылка на точку в Google Maps (при наличии координат). HTML экранируется; название ограничено 180 символами.

Фото: `TELEGRAM_MAX_PHOTOS` задаёт максимум JPEG/PNG (по умолчанию 3, диапазон 0–10; 0 — только текст), до 10 МБ каждый. Скачиваются локально и отправляются multipart через `sendPhoto`/`sendMediaGroup`. Для `*.sdn.cz` применяется обработка `fl=res,1200,1200,1|shr,,20|jpg,80`. Неудачный снимок пропускается. Без фото или при явном отклонении загрузки (400) отправляется текст. При таймауте/ограничении частоты уведомление остаётся неотправленным.

Для редактирования текстового сообщения используются `chat_id` и `message_ids[0]` с `editMessageText`, для фото/альбома — с `editMessageCaption`. При исчезновении из поиска и подтверждённом ответе detail API 404/410 добавляется `🔴 Gone ДД.ММ.ГГГГ` с сохранением исходного форматирования; дата первого обнаружения и статус редактирования сохраняются в `gone_at`/`gone_notified`. При сбое между принятием сообщения и сохранением статуса возможны дубли: exactly-once API не предоставляет. Токен бота не сохраняется; ответ Telegram может содержать данные чата, поэтому не публикуй `data/`.

## Логи

Логи выводятся в stderr через `log/slog` в формате `key=value` (время, уровень, сообщение, `module`, поля). По умолчанию `INFO`: запуск, начало/итоги сканирования и цикла, обнаружение объявлений, изменения хешей, извлечения, подавление и отправка уведомлений, обновления и `Gone`. Ошибки и повторные попытки — `WARN`, сбои цикла/хранилища — `ERROR`. Подробности (пагинация, загрузка detail/фото, кеш, причины отсева, сохранение файлов) — через `--debug`.

Тексты объявлений, контакты и токены в логи не выводятся; ошибки HTTP не содержат URL. ID объявлений, чатов и сообщений остаются в логах.
